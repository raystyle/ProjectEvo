# docs 六目录精确定义与方案模板

> 六目录的语义、分界与方案模板。决定「这份文档放哪」时查本篇。

## 一、六目录定义

| 目录 | 编号 | 语义 | 更新策略 |
| --- | --- | --- | --- |
| `docs\proven\` | PNNNN | **完全成功的 plan 方案归档** | 封存，不再更新 |
| `docs\diary\` | 日期 | 项目日记，一天一篇总结自省 | 当天写，不回改 |
| `docs\research\` | SNNN | 研究原型过程（为什么；验证了什么；别再踩什么） | 按需即时维护 |
| `docs\references\` | RNNN | **现役**做事的流程（操作手册、验收清单、发布流程） | 持续更新 |
| `docs\guide\` | GNNN | 做事的规范（标准与禁令） | 持续更新 |
| `docs\mistakes\` | M1xx/M0xx | 错误库 | 当场追加 |

## 二、分界口诀（高频易错）

> **方案做成归档进 proven（历史）；可复用流程提炼进 references（现役）；标准禁令进 guide。**

判定问题链：

1. 这是一份**已完成方案的完整记录**（做成了什么、当时依据）到 `proven\` PNNNN
2. 这是**下次照着做的操作流程**（怎么验收、怎么发版、怎么做选型检索）到 `references\` RNNN
3. 这是**必须遵守的标准或禁令**（命名怎么写、测试怎么分层、哪些字符禁用）到 `guide\` GNNN
4. 这是**为什么这么选/这么做的调研与实测** 到 `research\` SNNN
5. 这是**出错的记录与纠正** 到 `mistakes\` M 编号
6. 这是**今天做了什么的流水与自省** 到 `diary\` 日期文件

同主题横跨多类是正常的：一个特性落地 到 proven 归档方案；过程中踩的坑 到 mistakes；沉淀的操作手法 到 references；衍生的命名/测试标准 到 guide。

## 三、proven 目录（重点澄清）

**proven 不是里程碑，不是成果列表**，是**完全成功的 plan 方案的归档**：

- 立项时（R007 五步第 2 步）按 `docs\guide\template.md` 在 proven\ 建 `PNNNN-短名.md`，状态从「进行中」起步
- 方案文档**全程承载**：立项写背景/目标/方案/步骤，完成后回填「实施过程与经验」
- 验收全绿后状态转「已完成」，封存不再更新，记做成什么、当时依据
- 搁置的方案保留文档，状态标「搁置」；失败的尝试结论记 research 或 mistakes，不进 proven 充数

[经验： 2026-09-03 用户明确裁定「proven 不是里程碑，是完全成功 plan 方案的归档」]

## 四、方案模板（docs/guide/template.md)

```markdown
# 方案模板:新方案文档的写作骨架
> 新方案照此写。落点:docs\proven\PNNNN-短名.md。进行中与否以 TODO.md 为准。

- 状态:草案 / 进行中 / 已完成 / 搁置
- 日期:YYYY-MM-DD
- 关联:TODO 待办项 / 相关方案 / 研究

## 背景与问题
为什么需要这个方案,当前的问题是什么。

## 目标与非目标
- 目标:
- 非目标:

## 方案
核心设计、目录结构、关键命令。

## 备选方案
对比过的其他做法及取舍。

## 实施步骤
1. 2. 3.

## 风险与回滚
可能的风险、缓解措施、回滚方式。

## 实施过程与经验
> 完成时回填,不是留空。
- 实际怎么做(与计划偏差、关键决策点)
- 踩了什么坑 + 怎么解决(可引 mistakes 编号)
- 沉淀的经验(供后续方案直接套用)

## 验收标准
如何判断方案完成且正确。完成后在 diary 补一笔。
```

## 五、diary（项目日记）

- 文件名 `YYYY-MM-DD-主题.md`，一天一篇；一天多批时批次小节 + 收尾自省
- 与 proven 分工：diary 记当天流水与反思；方案与过程经验进 proven
- **口径纪律：概貌级**，工作细节归三原语与 proven,diary 防单文件膨胀（源仓曾单日十七批致 diary 超写，次日收缩回概貌级）[经验： ome 源仓 2026-09-02 自省]

### 收工自省五段模板（日终收尾）

```markdown
## 日记自省:收工总结
### 概貌        一段话:今天从 X 推到 Y,基线与提交数
### 关键裁决(用户)  当天用户拍板的口径与边界
### 得          验证过的原则(何以为对)
### 失与坑(明日带入) 二犯、返工、想当然——附明日动作
### 明日入口     下次会话从哪接手(待办指针、依赖回音)
```

[经验： ome 源仓 收工自省实践，概貌/裁决/得失/明日入口四件是交接最小集]

## 六、research（研究文档）

- 文件名 = 标题：博客式长标题，`-` 断句，不含空格/括号/冒号
- 结构必含**背景 + 关键结论**；按主题取舍：现状或实测、踩坑沉淀、待办
- 事实性断言标六态（见 base-writing-standards.md)
- 研究的产物是 PoC 原型：可运行验证落 `poc\<S编号-主题短名>\`，源码/清单/脚本/自述入仓，构建产物与模型 gitignore；上游 clone 实测类不搬源码，只记指针

## 七、mistakes（错误库）

两级结构：

- **分类文件 M1xx**：按错误族分类（如「Windows 路径与 shell 错误」「CI 与发布流水线错误」），一个文件覆盖一族
- **行级条目 M0xx**：一行一事：`M005 | 现象 | 根因 | 正确处理 | 首踩日期`
- 同根因或同型坑可合并聚合进已有条目（保留最早编号与首踩日期）；反复踩的坑升级落 research 分析
- 新分类文件建成登记 INDEX 错误速查节

**演化路径（允许从简起步）**：单文件 `MISTAKES.md`（一张表：现象/根因/正确处理/首踩）是合法起点，源头仓 与**最新的** 云 CLI 仓（2026-09-02 立项）都用单文件，错误族多了再拆 M1xx 分类文件（reader 仓 / 结构源仓 / ome 源仓演化形态） [实证： 五仓对照]

**diary 与 proven 的出身**：两目录本是同一个「history」，源头仓 08-29 将其拆分为 diary（当天流水账）与 history（方案+过程经验，即后来的 proven）。分界从诞生起就是「流水 vs 方案」 [实证： 源头仓 2026-08-29 重构日记]

## 八、编号规则

- 接当前最大号；P 四位、S/R/G 三位、M 全局递增、D 两位
- **退役编号不复用**；文档改名/迁移在 INDEX 留注记（如「R003 改 G005，2026-09-03,references/guide 归类修正」）
- **编号语义跨仓不对齐是常态**：同一号码在不同仓含义不同（实证：G004 在 结构源仓=经验沉淀细则、源头仓=字符规范、云 CLI 仓=中英文写作规范），**稳定的是类别语义（P/S/R/G/M/D），不是绝对号码**；跨仓引用写类别+主题，不裸写号码 [实证： 家族编号漂移三例]
